# 실험 기록

StyleForge 개발 과정에서 수행한 실험과 그 결과를 기록한다.
각 실험은 **가설 → 설정 → 결과 → 해석 → 결정** 순으로 작성한다.

> 작성 원칙
> - 실패한 실험도 기록한다. 실패 원인이 다음 실험의 근거가 된다.
> - 수치 없는 "좋아 보인다"는 쓰지 않는다. 판단 근거를 함께 남긴다.
> - 결정 사항은 `CLAUDE.md` 또는 `docs/dataset-aihub-minhwa.md`에 반영하고, 여기에 반영 여부를 적는다.

## E0. 데이터셋 스키마 실측 검증

**상태:** ✅ 완료
**대상:** AI 허브 「한국 전통 민화 제작 데이터」 (2025 구축)

### 배경
공식 데이터 설명서(HWP)에 라벨 JSON 스키마와 화목 분류 체계가 명시되어 있었다.
파서를 설계하기 전에 명세와 실제 데이터가 일치하는지 확인했다.

### 방법
1. `tree`로 실제 디렉터리 구조 확인
2. 화조도(HJ) 라벨 JSON 745건을 순회하며 필드값 분포 집계
3. 샘플 JSON 1건(`HJ_0001.json`)의 전체 구조를 육안 확인

### 결과 — 명세와 실제의 불일치 3건

| # | 항목 | 설명서 명세 | 실제 데이터 | 영향 |
|---|---|---|---|---|
| 1 | 화풍 필드명 | `painting_style` | **`painting_type`** | 명세대로 파싱 시 745건 전부 `None` 반환 |
| 2 | `drawing_type` 값 도메인 | 채색 / 수묵 / 수묵담채 (3종) | **12종 이상**, 복합값 존재 (`채색, 혁필` 등) | 완전 일치 매칭 필요. 부분 매칭 시 21건 오염 |
| 3 | `info` 블록 | 명세에 없음 | **존재** (version, copyright 등) | 저작권 문구 확보 — 이용 조건 근거로 활용 |

추가 확인 사항:
- **순번에 결번이 있다.** (예: `IM_0029` 부재) → 번호 순회 방식 금지, 디렉터리 목록 읽기 필수
- **`object_file_name`은 배열이 아닌 쉼표 구분 문자열** (`"HJ_0001_1, HJ_0001_2"`)
- **종횡비가 극단적이다.** 실측 예 317×1080 (약 1:3.4). 족자·병풍 형태가 다수

### 화조도(HJ) 실측 분포

`Training\01.원천데이터\TS_기본데이터_09.화조도` = **745장** (Validation 184장, 8:2 분할)

`drawing_type`:

| 값 | 장수 |
|---|---:|
| 채색 | 597 |
| 담채 | 32 |
| 낙화 | 29 |
| 수묵 | 18 |
| 기타 | 16 |
| 수묵, 담채 | 15 |
| 판화 | 15 |
| 채색, 혁필 | 13 |
| 판화, 채색 | 6 |
| 채색, 수묵 | 2 |
| 담채, 기타 / 기타, 채색 | 각 1 |

`채색` 597장 내 `painting_type`:

| 값 | 장수 |
|---|---:|
| 일필+공필 | 411 |
| 공필 | 160 |
| 일필 | 26 |

### 해석
공식 설명서를 그대로 신뢰해 파서를 작성했다면 화풍 필터가 조용히 실패해
전체 데이터가 무필터로 학습에 들어갔을 것이다. 필드가 `None`을 반환해도 예외가 발생하지 않으므로
학습 결과가 나빠진 뒤에야 원인을 역추적하게 된다.

종횡비 문제도 마찬가지다. 512×512 정사각 리사이즈를 기본값으로 두었다면
세로로 긴 족자 그림이 뭉개진 채 학습되어, 원인 불명의 품질 저하로 이어졌을 것이다.

### 결정
1. **파서는 실제 JSON을 기준으로 작성한다.** 필드 접근은 `.get()`, 값이 없으면 경고 후 항목 제외
2. **확정 학습 필터:** `HJ` + `drawing_type=채색` + `painting_type=일필+공필` → **411장**
   - 복합값 존재로 **완전 일치 매칭만 허용**
   - 대안: `painting_type=공필` 160장 (E3에서 비교)
3. **`enable_bucket=true` 필수** — `bucket_reso_steps=64`, `min_bucket_reso=256`, `max_bucket_reso=1024`
4. `scan.py`의 종횡비 이상치 기준을 1:4까지 정상으로 완화
5. 서브셋 선별은 파일명 파싱이 아닌 **디렉터리 선택**으로 처리 (폴더가 이미 화목별로 분리됨)

**반영:** `docs/dataset-aihub-minhwa.md` 2·3·3-1·3-2·5장, `CLAUDE.md` 2-(3)·3장

## E1. 캡션 소스 비교 — 제공 라벨(A) vs 자동 태깅(B)

**상태:** ✅ 완료 (2026-08-16)

### 가설
데이터셋이 제공하는 영문 캡션(`caption_eng`)을 가공해 쓰는 것이
WD14 tagger 자동 캡셔닝보다 화풍 학습 품질이 높을 것이다.
전문가가 작성한 캡션이 객체·구도를 더 정확히 기술하기 때문이다.

### 설정
| 조건 | A경로 (`hwajodo`) | B경로 (`hwajodo_b`) |
|---|---|---|
| 캡션 소스 | `caption_eng` (외부 라벨, 자연문) | WD14 tagger 자동 태깅 |
| 학습 데이터 | 동일 (HJ / 채색 / 일필+공필, `select_subset(seed=0)`로 뽑은 동일 40장) | 동일 |
| 하이퍼파라미터 | 동일 (`configs/train_default.toml` 기본값) | 동일 |
| 트리거 워드 | `hwajodo` | `hwajodo_b` (LoRA 파일명 충돌 회피용 — CLAUDE.md 규칙상 `--name`이 곧 트리거 워드라 A와 다를 수밖에 없다. 비교 자체에는 영향 없음) |
| 학습 소요 시간 | 5시간10분 (18618.88초) | 4시간5분 (14687초) |

A는 이미 학습돼 있던 `hwajodo`를 그대로 재사용했다(캡션이 자연문 형태인 것으로
A경로였음을 확인). B는 이번에 `--caption-mode auto`로 새로 학습했다.

**부수적으로 발견한 버그 2건** (E1 준비 중 WD14 tagger를 실제로 처음
돌리며 드러남 — 상세는 커밋 로그 참고):
1. `caption_auto.py`의 `STYLE_TAG_BLOCKLIST`가 공백 표기(`traditional media`)로
   적혀 있었는데 WD14 태그명은 danbooru 언더스코어 표기(`traditional_media`)라
   블록리스트가 전혀 매치되지 않고 있었다 — 화풍 태그가 안 걸러진 채로 캡션에
   들어가고 있었다는 뜻. `tag()`에서 언더스코어를 공백으로 바꿔 수정.
2. `train/runner.py`가 ComfyUI 재기동 헬스체크 타임아웃(기본 60초)을 넘기면
   `TrainRunnerError`를 그대로 던져서, 학습·LoRA 저장은 이미 끝났는데도
   `outputs/loras/{name}.json` 기록과 ComfyUI `models/loras` 복사가 통째로
   스킵됐다. 실제로 `hwajodo_b` 학습에서 재현됨(ComfyUI가 60초를 살짝 넘겨
   기동). 재기동 실패를 경고로만 남기고 후처리는 계속 진행하도록 수정,
   타임아웃도 180초로 상향.

### 결과
같은 화조도 소재 프롬프트 8종 × seed 4개 = 32장을 두 LoRA 각각으로
순수 txt2img 생성(`workflows/style_transfer_txt2img.json`, `lora_weight=1.0`,
측정 2와 동일 설정)해 비교했다.

| 지표 | A (`hwajodo`, 외부 라벨) | B (`hwajodo_b`, WD14) |
|---|---:|---:|
| CLIP Score | **0.7579** (min 0.6894, max 0.8104) | 0.7267 (min 0.6405, max 0.7709) |
| FID (vs 실사 91장) | 231.54 | **222.46** |

육안으로도 여러 쌍을 비교했다 — 예를 들어 같은 프롬프트("crane, pine tree")로
생성한 두 이미지는 학·소나무·낙관·비단 바탕까지 구도와 화풍 완성도가
육안으로는 거의 구분이 안 될 정도로 비슷했다.

### 해석
- **CLIP Score는 A가 일관되게 높다(+0.031, min/max 구간도 전부 A가 위).**
  자연어 프롬프트로 채점하는 지표이니, 학습 캡션 자체가 자연문(A)이었던 쪽이
  자연어 프롬프트에 더 잘 반응하도록 학습됐을 가능성이 크다 — "전문가 캡션이
  더 우수하다"는 가설과 방향은 일치하지만, 이게 "캡션 품질"의 효과인지
  "캡션 형식(자연문 vs 태그 나열)이 텍스트 인코더와 더 잘 맞는 효과"인지는
  이 실험만으로 분리가 안 된다.
- **FID는 오히려 B가 근소하게 낮다(-9.08).** 표본 32장 규모에서는 이 차이가
  노이즈 수준일 가능성이 높아 — 방향을 뒤집는 근거로 쓰기엔 약하다.
- **육안으로는 확실한 우열이 안 보인다.** 두 LoRA 모두 화조도 양식을 잘
  재현했다 — B(자동 태깅)도 "화풍 학습이 약하다"고 할 수준이 전혀 아니다.

**결론: A가 텍스트 프롬프트 정합성(CLIP Score)에서 작지만 일관된 우위를
보였고, 이는 가설과 방향이 일치한다.** 다만 격차가 크지 않고 FID·육안
평가로는 뒤집히거나 무승부에 가까워, "B경로는 쓰면 안 된다"고 결론 내릴
근거는 아니다. 데이터셋에 외부 라벨이 있으면 A를 기본으로 쓰되, 라벨이
없는 임의 폴더에서도 B경로로 이 정도 품질이 나온다는 게 이번 실험의
실질적 성과다.

### 결정
1. **CLAUDE.md 2-(2)의 A경로 우선 방침을 유지한다** — 라벨이 있으면 A, 없으면
   B라는 현재 `caption.py`의 자동 선택 로직은 그대로 둔다.
2. **버그 2건 수정을 코드에 반영·커밋함** (위 참고). 이번 실험이 아니었으면
   B경로 캡션이 화풍 태그를 계속 흘려보내고, 재기동이 느린 환경에서 학습
   메타데이터가 계속 누락됐을 것 — 다음 E2/E3 재학습부터 정상 동작한다.
3. **표본을 늘린 재검증은 후속 과제로 남긴다** — 32장으로는 CLIP Score
   격차(0.03)의 통계적 유의성을 주장하기엔 부족하다.

## E2. 학습 하이퍼파라미터 탐색

**상태:** ✅ 완료 (2026-08-16~17)

### 가설
8GB VRAM 제약 하에서 `network_dim`(rank)과 learning rate의 조합에 따라
화풍 재현도와 과적합 정도가 달라질 것이다.

### 설정
`configs/train_e2_exp{01,02,03}.toml`로 각각 새로 학습(HJ/채색/일필+공필,
`select_subset(seed=0)` 기준 동일 40장 — E1/hwajodo와 같은 모집단·같은 샘플).

| 실험 | network_dim | network_alpha | learning rate | 소요 시간 | 피크 VRAM |
|---|---|---|---|---:|---:|
| exp01 | 8 | 4 | 1e-4 | 36분 (2160.79초) | 7551 MiB |
| exp02 | 16 | 8 | 1e-4 | 44분48초 (2688.69초) | 7996 MiB |
| exp03 | 16 | 8 | 5e-5 | 46분45초 (2805.28초) | 7848 MiB |

공통: SD 1.5, `train_batch_size=2`, resolution 512, fp16, enable_bucket,
10 epoch, AdamW8bit, cosine scheduler, 40장. (`hwajodo`/E1과 달리 배치가
2라 총 스텝은 2,000 — 재사용 불가능해서 셋 다 새로 학습했다.)

### 결과
`docs/benchmarks.md` 측정 2·E1과 동일한 방법론으로 채점했다 — 화조도 소재
프롬프트 8종 × seed 4개 = 32장을 각 LoRA로 txt2img 생성(`lora_weight=1.0`),
CLIP Score는 생성 프롬프트 대비, FID는 실사 Validation 91장 대비.

| 실험 | CLIP Score | FID |
|---|---:|---:|
| exp01 (dim8, lr1e-4) | **0.7678** (min 0.7061, max 0.8447) | 244.74 |
| exp02 (dim16, lr1e-4) | 0.7615 (min 0.7105, max 0.8360) | **231.60** |
| exp03 (dim16, lr5e-5) | 0.7536 (min 0.6794, max 0.8180) | 240.98 |

셋 다 `hwajodo`(같은 방식으로 측정한 CLIP Score 0.7579, 레퍼런스 0.74)와
비슷한 구간에 있다 — 이 정도 범위 안에서는 하이퍼파라미터 조합이 극적인
차이를 만들지 않는다는 뜻이다. 육안으로도 exp01/exp02 샘플을 비교했는데
(학·소나무 프롬프트), exp02(dim16)의 깃털·바위 질감이 조금 더 섬세하게
나온 인상은 있었지만 exp01도 완성도 자체는 충분히 높았다 — 확정적인
우열로 보기엔 주관적인 인상에 가깝다.

### 해석
- **dim8 vs dim16 (lr1e-4 고정, exp01 vs exp02):** CLIP Score는 dim8이
  근소 우위(+0.006), FID는 dim16이 뚜렷 우위(-13.1). 신호가 지표마다
  갈려서 "rank를 올리면 무조건 좋아진다"는 근거는 안 된다.
- **lr1e-4 vs lr5e-5 (dim16 고정, exp02 vs exp03):** **CLIP Score·FID
  둘 다 lr1e-4가 더 좋다** (CLIP +0.008, FID -9.4) — 방향이 일관됐다.
  10 epoch로 고정한 상태에서 lr을 절반으로 낮추면 같은 스텝 수 안에
  충분히 수렴하지 못했을 가능성이 높다(과소학습). lr을 낮추려면 epoch
  수도 함께 늘려야 공정한 비교가 된다는 뜻이기도 하다.
- **VRAM: dim16(exp02) 7996 MiB가 8192 MiB 한계에 꽤 근접했다.** dim8(exp01)
  대비 445 MiB 더 쓴다 — 8GB에서 dim16 + batch2 조합은 여유가 많지 않으므로,
  다른 커스텀 노드나 배치 크기를 더 올리는 변경과는 같이 쓰기 어렵다.
- **소요 시간은 dim에 비례해 늘었다** (dim8 36분 < dim16 45~47분) — lr 차이
  (exp02 vs exp03)는 소요 시간에 영향 없음(예상대로, lr은 연산량과 무관).

### 결정
1. **`configs/train_default.toml`의 `network_dim=8`, `learning_rate=1e-4`
   기본값을 유지한다.** exp01(현재 기본값과 거의 동일 조건, batch만 다름)이
   CLIP Score 최고치를 기록했고, VRAM 여유도 가장 크다 — 8GB 제약 하에서
   "무난하게 잘 되는" 기본값이라는 CLAUDE.md 3장의 원래 근거가 실측으로도
   재확인됐다.
2. **`network_dim=16`을 쓰고 싶다면 `learning_rate`는 낮추지 말 것** —
   exp02(16/1e-4)가 exp03(16/5e-5)보다 두 지표 모두 우세했다. rank를
   올리는 것과 lr을 낮추는 것을 동시에 하면 상쇄돼 오히려 손해였다.
3. **dim16 + batch2 조합은 VRAM 여유가 크지 않다(8192 중 7996 사용)** —
   이 조합을 기본값으로 올리려면 `gradient_checkpointing`처럼 VRAM을
   더 아끼는 설정과 반드시 같이 검토해야 한다.
4. 표본 32장 규모의 한계는 E1과 동일하게 적용된다 — 격차가 크지 않은
   지표(CLIP Score 0.006~0.014 차이)는 노이즈일 가능성을 열어둔다.

## E4. style transfer 파라미터 스윕

**상태:** ✅ 완료 (denoise × lora_weight 2축. controlnet_strength 대조군은 범위 밖 — 아래 참고)

### 가설
img2img에서 `denoise`와 `lora_weight`는 트레이드오프 관계에 있다.
denoise가 낮으면 원본은 보존되나 화풍이 약하고, 높으면 화풍은 강하나 원본이 소실된다.
ControlNet으로 구조를 고정하면 **더 높은 denoise에서도 원본 보존이 가능**할 것이다.

### 설정
`styleforge sweep --style hwajodo`로 자동 탐색 (기본 4×4=16 조합):
- `denoise`: 0.35 / 0.50 / 0.65 / 0.80
- `lora_weight`: 0.40 / 0.60 / 0.80 / 1.00

(계획 단계에서 적은 0.4/0.55/0.7/0.85 대신 위 값을 썼다 — `sweep/planner.py`의
축 구간을 `apply/runner.py`의 `strength_to_params()`가 만드는 `--strength`
0~1 구간과 동일하게 맞췄기 때문. 두 값이 어긋나면 sweep으로 찾은 최적 조합을
`--strength` 하나로 재현할 수 없다.)

LoRA: `hwajodo` (화조도 HJ, `drawing_type=채색`+`painting_type=일필+공필` 40장,
10 epoch 실학습, `outputs/loras/hwajodo.safetensors`)

입력 이미지 3장 (개인 파이프라인 검증용으로만 사용, 재배포·학습에는 쓰지 않음):
- 풍경: 게임 스크린샷 (건물·하늘이 뚜렷한 구도)
- 인물: 반투명 배경의 게임 캐릭터 렌더
- 정물: 흰 배경 상품 사진(3D프린트 소품)

### 평가 지표
- **스타일 적용도:** 생성 이미지 ↔ 학습에 쓰인 화조도 레퍼런스 이미지(`data/prepared/hwajodo/*.jpg`
  중 5장 샘플) 평균 CLIP 유사도
- **원본 보존도:** 생성 이미지 ↔ 입력 이미지의 CLIP 유사도

### 결과

| 이미지 | denoise 0.35 → 0.80일 때 스타일 적용도 | 원본 보존도 | 권장 조합 |
|---|---|---|---|
| 풍경 | 0.461 → 0.600 (뚜렷한 증가) | 0.934 → 0.769 (뚜렷한 감소) | denoise=0.35, lora_weight=0.80 |
| 인물 | 0.408 → 0.412 (거의 무변화) | 0.954 → 0.858 (감소) | denoise=0.35, lora_weight=0.60 |
| 정물 | 0.450 → 0.456 (거의 무변화) | 0.983 → 0.938 (완만한 감소) | denoise=0.35, lora_weight=0.80 |

`lora_weight`는 세 이미지 모두에서 스타일/보존 어느 쪽에도 뚜렷한 단조 경향을
보이지 않았다 (변동폭이 측정 노이즈 수준).

### 해석
**풍경 이미지에서 가설이 명확히 검증됐다.** denoise를 올릴수록 스타일 적용도가
오르고 원본 보존도가 떨어지는 전형적인 트레이드오프가 나타났고, 비교 그리드
육안으로도 denoise가 높을수록 화조도 특유의 붓터치·색감이 강하게 얹히는 것을
확인했다. ControlNet lineart가 구조(건물 윤곽·수평선)는 denoise 0.8에서도
계속 붙잡고 있어 "구조는 유지하며 화풍만 강하게" 라는 설계 의도(CLAUDE.md
2-(1))가 실제로 동작함을 보여준다.

**인물·정물 이미지에서는 스타일 적용도가 denoise에 거의 반응하지 않았다.**
두 입력 모두 콘텐츠 도메인이 화조도(꽃·새·나뭇가지 위주 동양화)와 멀다 —
반투명 배경 게임 캐릭터, 흰 배경 상품 사진은 애초에 화조도 레퍼런스와의 CLIP
유사도 상한이 낮아서, 실제로 화풍이 더 강하게 입혀져도 지표가 잘 안 움직인다.
반면 원본 보존도는 두 이미지 모두 denoise에 따라 계속 하락했다 — 즉 이미지
자체는 계속 변형되고 있는데 "화조도스러워졌다"는 신호로는 안 잡힌다는 뜻이다.
**이는 가설의 반례가 아니라 CLIP 기반 스타일 적용도 지표의 한계다**: 콘텐츠
도메인이 학습 데이터와 동떨어진 입력일수록 이 지표의 민감도가 떨어진다.

### 결정
1. **denoise가 style/preservation 트레이드오프의 지배적 변수임을 확인.**
   `apply/runner.py`의 `strength_to_params()`가 `--strength`를 denoise에
   선형 비례시키는 현재 곡선의 방향성은 타당하므로 그대로 유지한다.
2. `lora_weight`는 이번 표본으로는 유의미한 방향성을 못 찾았다 — 곡선을 바꿀
   근거가 부족하므로 현재 매핑을 유지하고, 표본을 늘린 재실험을 후속 과제로
   남긴다.
3. **CLIP 스타일 적용도 지표는 콘텐츠 도메인이 학습셋과 가까운 입력(예:
   실사 풍경·건축물)에서 가장 신뢰도가 높다.** 사용자 가이드에 "인물·상품
   사진보다는 풍경·정물 사진에서 sweep 결과가 더 명확하다"는 참고를 남길 것
   (Phase 5 문서화 항목).
4. **controlnet_strength(0.0 대조군 vs 0.6) 비교는 이번에 다루지 못했다** —
   `sweep`이 그리드 이미지를 2차원으로 유지하기 위해 축을 최대 2개로
   제한하는 설계라서다(`sweep/planner.py`). 3축 전수비교가 필요하면 별도
   스크립트나 axes 확장이 필요하다 — 후속 과제로 남긴다.

**반영:** `apply/runner.py`의 `strength_to_params()` 변경 없음(현재 곡선 유지 확인).

**후속 과제 3건 완료 (2026-08-16, 재학습 없이 진행 — 상세는 `docs/benchmarks.md`
2~3장):**
- `lora_weight` 재검증 — 풍경 이미지 1장으로 8단계까지 재탐색해도 방향성 없음을
  재확인. 곡선 변경 근거 없음을 확정.
- `controlnet_strength` on/off 대조군 — denoise=0.80 고정, 0.0 vs 0.6 비교.
  세 도메인 모두에서 "켜면 원본 보존도 ↑, 스타일 적용도 소폭 ↓"가 일관되게
  나타나 CLAUDE.md 2-(1) 설계 의도를 실측으로 뒷받침.
- 순수 txt2img 기반 CLIP Score/FID 재측정 — 새 워크플로우
  `workflows/style_transfer_txt2img.json` 추가. 학습 캡션 어휘 기반 프롬프트로
  화조도 도메인에 맞춰 32장 생성. CLIP Score 0.7579로 레퍼런스(0.74)와 대등한
  수준까지 개선(img2img 측정 시 0.5609였음) — img2img 스윕의 낮은 수치가
  "화풍 학습이 약해서"가 아니라 "평가 입력 도메인이 안 맞아서"였음을 뒷받침.
