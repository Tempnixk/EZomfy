# 벤치마크 — 8GB VRAM 제약 하 파라미터 근거 및 레퍼런스 대비 위치

> 이 문서의 목적은 "레퍼런스보다 낫다/못하다"를 주장하는 게 아니다. 학습 조건이
> 동일하지 않으므로 우열은 판단하지 않고, **공개된 레퍼런스 대비 우리 설정이
> 대략 어느 위치에 있는지**를 조건 차이와 함께 기록한다 (CLAUDE.md 2-(4)).

## 1. 8GB VRAM(RTX 3060 Ti) 제약 하 학습 파라미터 근거

`configs/train_default.toml`의 기본값과 그 이유:

| 파라미터 | 값 | 근거 |
|---|---|---|
| base model | SD 1.5 | SDXL은 8GB에서 LoRA 학습이 사실상 불가능(base UNet만 여러 GB) — CLAUDE.md 3장에서 SDXL 코드 자체를 금지 |
| `resolution` | 512 | SD1.5 네이티브 해상도. 이 이상 올리면 latent 캐시·activation 메모리가 제곱으로 늘어 8GB에서 batch_size=1도 위태로워짐 |
| `network_dim` | 8 | LoRA rank. 8~16 권장 구간의 하한 — 8GB에서 여유를 더 남기려는 선택. **E2(`docs/experiments.md`, 완료)로 실측 검증됨**: dim16은 dim8보다 VRAM을 445MiB 더 쓰고(8192 중 7996 사용, 여유가 크지 않음), CLIP Score/FID로는 dim8과 뚜렷한 우열이 없었다 — 현재 기본값 유지 근거로 충분하다 |
| `network_alpha` | 4 | `network_dim`의 절반. kohya 권장 관례(alpha=dim/2)를 따름 — dim과 별도로 조정할 근거가 아직 없어 관례값 유지 |
| `train_batch_size` | 1 | 8GB에서 batch 2 이상은 `resolution=512` + `network_dim=8` 조합에서도 OOM 위험이 커 가장 보수적인 값을 기본으로 함 |
| `mixed_precision` | fp16 | fp32 대비 activation 메모리를 절반으로 줄임 — 8GB에서는 사실상 필수 |
| `gradient_checkpointing` | true | activation을 저장하지 않고 backward 시 재계산 — VRAM을 크게 아끼는 대신 학습 속도가 떨어지는 트레이드오프. 8GB에서는 VRAM이 항상 더 급한 자원이라 켜둠 |
| `cache_latents` | true | 매 스텝 VAE 인코딩을 반복하지 않고 미리 계산해 캐싱 — VRAM보다는 학습 속도 최적화지만, VAE를 학습 루프 중 계속 GPU에 올려둘 필요가 없어져 간접적으로 VRAM에도 도움 |
| `optimizer_type` | AdamW8bit | bitsandbytes의 8bit 옵티마이저. 일반 AdamW 대비 옵티마이저 상태(모멘텀·분산) 메모리를 1/4로 줄임 — 8GB에서 다른 여유를 만들어주는 항목 |
| `enable_bucket` | true | 민화 데이터셋은 족자·병풍 형태로 종횡비가 극단적(실측 1:3.4)이라 정사각 강제 리사이즈 시 구도가 파괴됨 (`docs/dataset-aihub-minhwa.md` 3-2장). VRAM보다는 데이터 품질 문제지만, 여기 함께 기록 |

### 실측: 실제 학습 실행 (hwajodo, 2026-08-13)

| 항목 | 값 |
|---|---|
| 데이터 | 화조도(HJ), `drawing_type=채색`+`painting_type=일필+공필`, 40장 |
| 총 스텝 | 4,000 (40장 × 10 repeats × 10 epoch, batch_size=1) |
| 소요 시간 | 5시간 10분 (18,618.88초) |
| 스텝당 속도 | 초반 ~11s/it → 후반 ~4.6s/it (가속 — 원인 미분석, 디스크 캐시·버킷 재사용 등으로 추정) |
| 결과 | OOM 없이 10 epoch 완료, `outputs/loras/hwajodo.safetensors` (18.9MB) 생성 |
| GPU | RTX 3060 Ti, VRAM 8192MB, 드라이버 CUDA 13.1, torch 2.13.0+cu130 |

**피크 VRAM 수치는 별도로 로깅하지 않았다** (kohya 로그에 VRAM 사용량 출력이
없었음) — 다만 위 설정으로 OOM 없이 완주했다는 사실 자체가 "이 조합이 8GB
안에서 동작한다"는 실증이다. 정확한 피크 값이 필요하면 `nvidia-smi
--query-gpu=memory.used --format=csv -l 1`을 학습과 병행 실행해 로깅하는
것을 후속 과제로 남긴다.

## 2. apply 파라미터 매핑 곡선 근거

`apply/runner.py`의 `strength_to_params()`는 `--strength`(0~1)를 아래 구간에
선형 매핑한다:

| 파라미터 | strength=0 | strength=1 |
|---|---|---|
| `denoise` | 0.35 | 0.80 |
| `lora_weight` | 0.40 | 1.00 |
| `controlnet_strength` | 0.60 | 0.95 |

**E4 실험(`docs/experiments.md`)으로 이 곡선의 방향성을 실측 검증했다:**
- `denoise`가 style/preservation 트레이드오프의 지배적 변수임을 확인 — 곡선에서
  denoise를 strength에 선형 비례시키는 현재 설계가 타당함을 재확인했다.
- **`lora_weight` 재검증 완료 (2026-08-16):** 풍경 이미지 1장으로 축을
  8단계까지 촘촘히 재탐색했다(`--axes lora_weight --steps 8`). 스타일
  적용도 0.476~0.539, 원본 보존도 0.818~0.921 범위에서 오르내림만 있고
  단조 경향은 여전히 없었다 — E4의 결론(표본 4단계에서 방향성 없음)이
  해상도를 높여도 그대로 재현됐다. **곡선을 바꿀 근거가 없다는 결론을
  확정한다.** (표본이 이미지 1장이라는 한계는 남지만, 같은 이미지 안에서
  촘촘히 재본 결과이므로 "표본이 적어서 놓쳤다"는 가능성은 상당히 줄었다.)
- **`controlnet_strength` on/off 대조군 비교 완료 (2026-08-16):** `sweep`의
  2축 제한을 피해 `run_apply_with_params()`를 직접 호출, denoise=0.80(최댓값,
  구조가 가장 무너지기 쉬운 지점)·lora_weight=0.70 고정하고 controlnet_strength만
  0.0(끔) vs 0.6(켬)으로 비교했다(3장 각 1쌍, 같은 seed).

  | 이미지 | 스타일 적용도 (off→on) | 원본 보존도 (off→on) |
  |---|---|---|
  | 풍경 | 0.550 → 0.494 (−0.055) | 0.729 → 0.860 (+0.131) |
  | 인물 | 0.613 → 0.422 (−0.190) | 0.664 → 0.845 (+0.182) |
  | 정물 | 0.545 → 0.420 (−0.126) | 0.809 → 0.944 (+0.135) |

  **denoise/lora_weight 스윕과 달리 세 도메인 모두에서 신호가 일관됐다** —
  ControlNet을 켜면 원본 보존도가 뚜렷이(+0.13~0.18) 오르고 스타일 적용도는
  완만히(−0.06~0.19) 내려간다. "ControlNet이 구조를 붙잡아 높은 denoise에서도
  원본을 지킨다"는 CLAUDE.md 2-(1) 설계 의도가 실측으로 확인됐다. 원본
  보존도 지표는 생성-원본 이미지 간 직접 비교라 콘텐츠 도메인에 덜 민감한
  것으로 보인다(스타일 적용도는 화조도 레퍼런스와의 비교라 도메인에 민감).

## 3. 입력 이미지 리사이즈 누락으로 인한 apply/sweep 성능 저하 (발견·수정, 2026-08-17)

### 증상
GUI에서 sweep을 돌렸는데 조합 하나가 15~17분씩 걸려, 기본 16조합(`denoise×lora_weight`,
4×4)이 총 4시간 이상 걸릴 것으로 추정되는 상황이 발생했다.

### 원인
`workflows/style_transfer_lineart.json`이 `LoadImage`로 읽은 원본 이미지를 리사이즈
없이 그대로 `VAEEncode`/`LineArtPreprocessor`에 넘기고 있었다. SD1.5는 512px 기준으로
학습된 모델인데, 입력이 스마트폰 사진 원본(예: 4032×3024, 1200만 화소)처럼 크면:
- VAE가 8GB VRAM에서 정상 인코딩/디코딩에 실패해 타일 모드로 폴백
  (`Ran out of memory when regular VAE encoding/decoding, retrying with tiled...`)
- KSampler가 스텝당 43.08초까지 느려짐 (정상 범위: 1~2초/스텝)

ComfyUI 자체 로그(`ComfyUI/user/comfyui.log`)에서 직접 확인:
```
100%|██████████| 20/20 [14:20<00:00, 43.08s/it]
```

### 수정
- `workflows/style_transfer_lineart.json`에 `ImageScale` 노드(id `13`)를 추가하고
  `LoadImage → ImageScale → VAEEncode`/`LineArtPreprocessor`로 재배선했다. 원본
  비율은 유지한 채 긴 변만 512px에 맞춘다 — 정사각 크롭이나 강제 리사이즈로
  구도를 깨지 않기 위함이다(민화 원본의 극단적 종횡비를 다루는 1장 `enable_bucket`
  근거와 같은 이유). 워크플로우는 여전히 데이터로 취급하고(CLAUDE.md 6장),
  노드 그래프 자체는 ComfyUI에서 내보낸 JSON을 그대로 둔 채 노드만 추가·재배선했다.
- `apply/runner.py`에 `_fit_to_target_side()`를 추가해 입력 이미지 크기를 보고
  매 요청마다 리사이즈 목표 width/height를 계산하고, 기존 파라미터 주입 경로
  그대로(`workflows/mappings/style_transfer_lineart.toml`에 `resize_width`/
  `resize_height` 매핑 추가) 워크플로우에 넘긴다.
- `sweep`은 내부적으로 `apply`의 `run_apply_with_params()`를 그대로 재사용하므로
  별도 수정 없이 함께 해결됐다.

### 실측 비교

**apply 1회**

| 조건 | 입력 해상도 | 소요 시간 |
|---|---:|---:|
| 수정 전 (동일 사진, sweep 조합으로 측정 — 동일 워크플로우) | 4032×3024 (리사이즈 없음) | 907.7~1031.2초 (n=3) |
| 수정 전 (다른 사진) | 1920×1080 (리사이즈 없음) | 36.9~168.2초, 평균 ~107초 (n=4) |
| **수정 후** (위와 동일한 4032×3024 사진) | 512×384로 리사이즈 | **6.98초** |
| **수정 후** (다른 사진) | 344×512로 리사이즈 | **3.45초** |

동일 사진(4032×3024) 기준 **약 136배** 단축 (≈951초 → 6.98초).

**sweep 1회 (기본 16조합, `denoise × lora_weight`)**

| 조건 | 조합당 평균 소요 | 전체 sweep |
|---|---:|---:|
| 수정 전 | 951.7초 (n=3 실측: 1031.2 / 907.7 / 916.2초) | 3개 조합 실측치로 외삽 시 **약 4.2시간** |
| **수정 후** | 3.57초 (n=12 실측, 범위 3.25~4.36초) | 12개 조합 합계 42.78초 — 16개 전체도 **약 1분 이내** |

**약 250배 이상 단축** (약 4.2시간 → 약 1분).

### 결론
apply/sweep 워크플로우는 입력 이미지 크기에 대한 가정이 전혀 없었다 — 학습
데이터(이미 512px대로 전처리된 이미지)로만 검증했을 때는 드러나지 않았던
문제였다. 실사용에서는 스마트폰 사진 같은 대형 원본을 그대로 넣는 것이
일반적인 사용 패턴이므로, 이번 수정은 특정 케이스의 최적화가 아니라
**정상적인 사용 시나리오에서 상시 발생하던 결함의 수정**에 가깝다.

## 4. AI 허브 공개 레퍼런스 대비 CLIP Score / FID

구축기관이 동일 데이터로 수행한 레퍼런스 구현(Stable Diffusion + LoRA Fine
Tuning)의 공개 수치:

| 지표 | 레퍼런스 |
|---|---|
| CLIP Score | 0.74 |
| FID | 25.5 |

### 측정 1 — E4 img2img 스윕 결과 재사용 (2026-08-16)

`evaluate/metrics.py`의 `clip_text_score()`(Hessel et al. CLIPScore 정의,
w=2.5)와 `compute_fid()`(pytorch-fid, InceptionV3 pool3 활성값)로 산출했다.
생성 이미지는 새로 만들지 않고 **E4 스윕에서 이미 생성된 48장**(풍경/인물/
정물 각 16조합, `hwajodo` LoRA, 프롬프트 `"hwajodo, best quality"`)을
재사용했고, 실사 기준셋은 `Validation\01.원천데이터\VS_기본데이터_09.화조도`
91장을 그대로 썼다.

| 지표 | 우리 측정값 | 레퍼런스 | 표본 수 |
|---|---:|---:|---|
| CLIP Score | 0.5609 (min 0.5106, max 0.6080) | 0.74 | 생성 48장 |
| FID | 386.21 | 25.5 | 생성 48장 vs 실사 91장 |

FID 386.21은 레퍼런스(25.5)와 자릿수부터 다른데, 아래 캐비앗 중 특히
**도메인 불일치**가 지배적 원인으로 보인다 — 48장 중 32장(인물·정물)이
화조도와 무관한 입력(게임 캐릭터 렌더, 상품 사진)에서 나온 img2img
결과라, 화조도만 담긴 91장 실사 세트와 분포 자체가 크게 벌어진다.
CLIP Score(0.5609)도 같은 이유로 레퍼런스보다 낮게 나왔을 가능성이 크다.

### 측정 2 — 순수 txt2img 재측정 (2026-08-16, 후속 과제 5번 완료)

측정 1의 가장 큰 문제(img2img 입력 도메인 불일치)를 없애기 위해 새
워크플로우를 만들었다: `workflows/style_transfer_txt2img.json` — 입력
이미지·ControlNet 없이 `체크포인트 → LoRA → CLIPTextEncode → KSampler(denoise=1.0)
→ VAEDecode`로만 구성된 순수 txt2img. (다른 워크플로우와 동일하게 노드 그래프는
ComfyUI가 실행하는 JSON 데이터고, 매핑은 `workflows/mappings/style_transfer_txt2img.toml`에 있다.)

프롬프트는 학습 캡션 어휘(`data/prepared/hwajodo/*.txt`)에서 뽑은 화조도
소재 8종(불사조·모란, 꿩·동백, 매화·새, 비둘기·모란, 원앙·버들·붓꽃,
학·소나무, 까치·매화, 연꽃·원앙) × seed 4개 = 32장을 생성했다
(`lora_weight=1.0`). CLIP Score는 각 이미지를 **생성에 쓴 그 프롬프트와**
비교해 산출했다(표준 CLIPScore 방법론과 동일). FID의 실사 기준셋은
측정 1과 같은 91장.

| 지표 | 우리 측정값 | 레퍼런스 | 표본 수 |
|---|---:|---:|---|
| CLIP Score | **0.7579** (min 0.6894, max 0.8104) | 0.74 | 생성 32장 |
| FID | **231.51** | 25.5 | 생성 32장 vs 실사 91장 |

**CLIP Score는 레퍼런스와 거의 같다(오히려 근소하게 높다).** 도메인을
맞추자 측정 1의 0.56에서 0.76으로 크게 올랐다 — 측정 1의 낮은 값이
"화풍 학습이 약해서"가 아니라 "평가 입력이 화조도와 무관해서"였다는 게
이걸로 뒷받침된다. 생성물을 육안으로도 확인했는데(학·소나무, 꿩·동백
등) 낙관·인장·비단 바탕까지 포함해 화조도 양식을 잘 재현했다.

FID는 386→232로 개선됐지만 여전히 레퍼런스(25.5)와는 거리가 멀다 —
표본 32장·91장은 FID가 요구하는 표본 규모(보통 수천 장)에 한참 못
미쳐 분산이 매우 크다는, 아래에 정리한 근본적 한계가 여기서는 남는다.

### 이 수치를 읽을 때 반드시 감안할 것 (우열 판단 근거로 쓰지 않는 이유)

- **표본 수가 논문 수준 FID(보통 수천~수만 장)에 비해 훨씬 작다.** 32~48장·91장
  규모의 FID는 분산이 매우 커서 절대값 자체의 신뢰구간이 넓다. 측정 2로
  조건을 레퍼런스에 최대한 맞춘 뒤에도 FID가 여전히 큰 차이를 보이는 건
  대부분 이 표본 규모 문제로 보인다.
- **학습 규모가 다르다.** 우리 LoRA는 40장·10epoch(rank 8)로 학습했고,
  레퍼런스의 정확한 학습 규모는 공개 자료에 명시되어 있지 않다.
- **레퍼런스의 정확한 생성 조건(프롬프트 구성, 샘플러, 스텝 수 등)이
  공개되어 있지 않다.** 측정 2는 "프롬프트 기반 txt2img일 것"이라는
  추정 하에 조건을 맞춘 것이지, 확인된 사실은 아니다.

**결론: 측정 2(txt2img, CLIP Score 0.7579)는 레퍼런스와 조건을 최대한
맞춘 결과이고 CLIP Score만 놓고 보면 레퍼런스와 대등한 수준까지 왔다고
읽을 수 있다.** 다만 FID는 표본 규모 한계 때문에 여전히 참고용 좌표
이상으로 쓰지 않는다 — 표본을 최소 수백 장으로 늘리는 재실험을 후속
과제로 남긴다.
